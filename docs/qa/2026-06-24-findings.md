## [HIGH|data-loss] src/lib/profileSync.ts:25
**Failed onboarding/profile writes replay onto whatever account is signed in next (cross-account preference leak)**

The pending-profile stash key is a single global localStorage key `numa:profile:pending` (line 25), not scoped per account. When a `pushProfile` write fails (offline/socket drop) it is merged into this global stash (mergePendingProfilePatch, lines 64-74). The retry effect in usePushProfile (lines 104-118) blindly flushes the whole stash to `api.profiles.updateProfile` on the next mount for the CURRENTLY signed-in user. Neither signOut nor deleteAccount in src/services/auth.tsx ever clears this key. updateProfile (convex/profiles.ts:236-263) only checks `auth.getUserId` and applies appMode/themeKey/locale/onboardingCompletedAt to that user with no ownership/account check. So user A's failed onboardingCompletedAt + appMode + themeKey can be written onto user B's profile.

_Fix:_ Scope the stash per account id. Capture the current account id when stashing (e.g. key `numa:profile:pending:<accountId>` or store `{accountId, patch}`), and in usePushProfile's retry effect only flush the stash whose account id matches the currently signed-in account (discard or ignore a mismatched stash). Additionally clear the current account's pending key in auth.tsx signOut (415-425) and deleteAccount (alongside the existing per-account removeItem calls at 479-482). The retry effect must take the active account id as a dependency so it re-evaluates on account switch. As a defense-in-depth measure, the minimal version is: store the account id alongside the patch and have the flush discard the stash entirely when the active account id differs.

## [HIGH|data-loss] src/services/writeQueue.tsx:366
**Transient write failure while online is enqueued as "failed" and never retried or surfaced — silent data loss**

In runOrQueue, when cloud is enabled and the device is online but a mutation throws a transient error (network blip, websocket drop, timeout — matched by isTransientWriteError), the write is enqueued with status "failed" (not "pending") and the call returns { queued: true } as if it succeeded. flushPending (line 280-283) only ever iterates items with status === "pending", and the pendingSignature effect (line 385-391) only fires for pending items. Net result: a transaction/asset/goal/pod write that hits one transient error while the user is online is permanently lost and silently dropped, while the calling action reported success.

_Fix:_ In runOrQueue (writeQueue.tsx:364-368), enqueue transient failures with status:"pending" instead of "failed" so the pendingSignature effect and flushPending pick them up immediately and after reload. To preserve the test's intent of not looping forever, add a backoff/attempt cap inside flushPending (e.g. stop re-promoting after N attempts) rather than relying on a permanent "failed" terminal state that only the 'online' event can escape. ## [HIGH|data-loss] src/routes/pod/page.tsx:2520
**Pod expense batch-save: partial network failure loses later entries and duplicates earlier ones**

In the ExpenseSheet save handler, batch quick-add iterates `for (const [index, entry] of batchEntries.entries()) { await actions.addPodExpense(...) }`. Each addPodExpense in the cloud path calls `mutations.addPodExpense(...)` DIRECTLY (podActions.ts:348) and does NOT go through queue.runOrQueue, so it is neither offline-queued nor idempotency-protected on retry. If a transient failure occurs partway through the loop (say on entry 3 of 5), the await rejects, the loop aborts, entries 1-2 are already committed server-side, entries 3-5 are silently dropped, and the catch shows a generic 'couldn't save' error. The user naturally retries the whole batch — but addPodExpense mints a fresh clientMutationId per call, so the already-committed entries 1-2 are re-inserted as DUPLICATE expenses. Net result: lost expenses plus double-counted ones, corrupting every shared-pot balance and settlement amount.

_Fix:_ Route addPodExpense's cloud path through runQueuedCloudMutation like its siblings so failures are queued/retried idempotently. For the batch specifically, generate a stable clientMutationId per entry ONCE before the loop (e.g. derive deterministically from a batch UUID + index, or hold the array in component state) and reuse those exact IDs on retry, so re-submitting the whole batch hits the existing mutationReceipts for already-committed entries (no duplicates) while still completing the dropped ones (no loss). Alternatively add a single backend batchAddExpenses mutation that inserts all entries in one transaction under one clientMutationId, making the whole batch atomically all-or-nothing.
